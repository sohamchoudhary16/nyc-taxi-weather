## Why quarantine rather than filter

A dropped row is invisible. A quarantined row has a `failure_reason`, gets
counted in the DQ metrics table, and can be replayed after a rule is fixed.
Silently filtering is how you lose revenue you cannot reconcile.

## Approach

Each DQ rule is expressed as a named boolean column in `stg_trips.sql`
(e.g. `dq_non_positive_duration`, `dq_pickup_out_of_range`). The `is_valid`
flag is the conjunction of the hard-fail rules; soft flags (zero passengers,
negative fares) are kept for downstream filtering decisions.

In production I would emit a DQ metrics table per pipeline run (rows in,
rows passed, rows quarantined by rule) and alert on drift — a sudden spike
in quarantined rows usually means a schema change upstream, not a data
quality improvement.

## Resolved: weather timestamps displayed with local offset

**Observed:** Weather range showed `+01:00` (e.g. `2023-12-31 01:00:00+01:00`)
instead of UTC, suggesting the system's `Europe/Berlin` locale was leaking
into the data.

**Investigation:** Traced the full path from Open-Meteo API → `ingest_weather.py`
→ `timestamps.normalise()` → `load_duckdb.py` → DuckDB bronze table. The API
is called with `timezone=UTC`. The normaliser receives `source_tz="UTC"`,
parses naive ISO strings, and `tz_localize`s with an explicit `ZoneInfo("UTC")`
— the system locale never enters the code path.

**Verification query:**
```sql
SET TimeZone='UTC';
SELECT min(observed_at_utc), max(observed_at_utc) FROM bronze.weather;
-- Returns: 2023-12-31 00:00:00+00:00 .. 2024-02-01 23:00:00+00:00

SET TimeZone='Europe/Berlin';
SELECT min(observed_at_utc), max(observed_at_utc) FROM bronze.weather;
-- Returns: 2023-12-31 01:00:00+01:00 .. 2024-02-02 00:00:00+01:00
-- Same instant, different display.
```

**Root cause:** DuckDB stores `TIMESTAMPTZ` as UTC internally but *renders* it
in the session's local timezone. On a machine set to `Europe/Berlin`, a
`SELECT` displays `+01:00` (CET) or `+02:00` (CEST). This is a display
artefact, not a storage bug — the underlying instant is correct.

**Fix:** Added `SET TimeZone='UTC'` to the DuckDB session in `load_duckdb.py`
immediately after connecting, so all reads and writes use an explicit UTC
session regardless of the host's locale.

## Investigated: fare reconciliation gap (25.69%)

**Observed:** 761,730 rows (25.69%) where `total_amount` differs from the sum
of its component columns by more than $0.01.

**Query:**
```sql
SELECT
    round(total_amount - (fare_amount + extra + mta_tax
        + coalesce(improvement_surcharge,0) + tip_amount
        + tolls_amount + coalesce(congestion_surcharge,0)
        + coalesce(Airport_fee,0)), 2) as gap,
    count(*) as n
FROM bronze.trips WHERE total_amount > 0
GROUP BY 1 ORDER BY n DESC LIMIT 15
```

**Findings:**

| Gap ($) | Rows | Interpretation |
|---|---|---|
| 0.00 | 2,166,974 | Reconciles perfectly (73.1%) |
| -2.50 | 590,939 | `congestion_surcharge` in column but excluded from `total_amount` |
| +2.50 | 129,330 | `congestion_surcharge` in `total_amount` but column is 0/null |
| -4.25 | 22,451 | Likely congestion + airport fee mismatch |
| -1.75 | 18,149 | Partial surcharge inconsistency |

**Conclusion:** The formula includes every column in the schema (verified via
`DESCRIBE bronze.trips` — no `cbd_congestion_surcharge` exists). The gap is a
**known TLC data inconsistency**: the surcharge columns and `total_amount` are
populated by different systems and do not always agree. This is not a pipeline
bug — it is a source-data finding.

**Action:** Flag, do not quarantine. In production, surface this in a
reconciliation dashboard so finance can investigate the discrepancy per vendor.
